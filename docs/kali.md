# Kali Linux в VirtualBox

Агент запускается в Windows. `VBoxManage` запускает зарегистрированную VM,
OpenSSH отправляет команды в Kali, а QTerminal или `xterm` показывает команду и настоящий
вывод на рабочем столе гостя. **PNG снимается в Windows с окна VirtualBox через
PrintWindow вместе с рамкой окна.** В Kali снимки не создаются. Снимок всего
рабочего стола Windows вместо окна не используется.

Windows остаётся доступной: ввод с клавиатуры и мышь хоста не используются.
Окно VirtualBox можно перекрывать другими окнами. Оно должно оставаться
развёрнутым в обычном оконном режиме, с работающим графическим сеансом Kali.
Работа захвата на другом виртуальном рабочем столе Windows требует отдельной
проверки. Headless, свёрнутое окно и заблокированный гостевой сеанс не подходят
для доказательства результата команды. Если PrintWindow не отдаёт картинку
гостя, шаг блокируется; захват экрана не подставляется.

Сейчас поддержан VirtualBox и X11. VMware, Hyper-V, Wayland и управление
произвольными GUI-программами внутри гостя этой интеграцией не реализованы.
Интерактивные команды, требующие пароля или диалога, не подходят для `kali.run`.
Для административных команд заранее настройте необходимые права; `sudo -n`
возвращает ошибку вместо ожидания ввода. Используйте копии учебных данных.

На этом ПК подключение настроено и проверено 2026-10-15: VM
`e7aff680-294a-46b8-8744-57732aaaaad2`, SSH `kali@127.0.0.1:2222`,
отдельный ключ `~/.ssh/doneasik_kali`, QTerminal 2.4.0. Параметры сохранены в
локальном `config.yaml`, который исключён из git. Для новых заданий достаточно:

```powershell
py -3.12 -m lab_agent.cli do workspace/MyKaliLab kali.start
py -3.12 -m lab_agent.cli do workspace/MyKaliLab kali.run -p command=id
py -3.12 -m lab_agent.cli do workspace/MyKaliLab kali.run -p script=working/commands.sh
```

При выполнении агент временно предотвращает включение заставки Kali; срок
ограничен таймаутом команды плюс 30 секунд. Настройки блокировки не меняются.
Заблокированный графический сеанс нужно разблокировать вручную.

## Первая настройка SSH

1. В Kali войдите в графический сеанс своим пользователем. В её терминале:

   ```bash
   sudo apt update
   sudo apt install openssh-server x11-utils
   command -v qterminal || command -v xterm
   sudo systemctl enable --now ssh
   echo "$DISPLAY"
   echo "${XAUTHORITY:-$HOME/.Xauthority}"
   ```

   Если ни один терминал не найден, установите `qterminal` или `xterm`.

2. Для NAT в VirtualBox добавьте проброс порта в настройках VM:
   **Network → Adapter 1 → Advanced → Port Forwarding**.
   Имя `doneasik-ssh`, протокол TCP, Host IP `127.0.0.1`, Host Port `2222`,
   Guest IP пустой, Guest Port `22`. Если saved state не позволяет изменить
   настройку, сначала штатно завершите Kali, затем настройте проброс и запустите VM.
   Host IP должен быть именно `127.0.0.1`, чтобы SSH не выставлялся в локальную сеть.

3. В PowerShell Windows создайте отдельный ключ (существующий не перезаписывать):

   ```powershell
   ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\doneasik_kali"
   ```

   Ключ с парольной фразой заранее загрузите в `ssh-agent`; автоматический запуск
   использует `BatchMode=yes` и не спрашивает пароль.

4. Подставьте свой логин Kali вместо `kali`. Первый раз подключитесь вручную,
   проверьте отпечаток ключа сервера и подтвердите его. Отпечаток в Kali можно
   посмотреть командой `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.

   ```powershell
   ssh -p 2222 kali@127.0.0.1
   ```

   После первого подключения скопируйте публичный ключ из Windows:

   ```powershell
   Get-Content "$env:USERPROFILE\.ssh\doneasik_kali.pub" | ssh -p 2222 kali@127.0.0.1 'umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys'
   ssh -i "$env:USERPROFILE\.ssh\doneasik_kali" -p 2222 -o BatchMode=yes -o StrictHostKeyChecking=yes kali@127.0.0.1 id
   ```

   Пароль вводится только в ручном SSH-сеансе. Приватный ключ не копируется в
   workspace и не передаётся в гостевую систему.

## Выполнение

Все действия доступны через реестр capabilities и AI-планировщик. У
`kali.run` риск `unsafe`: при выполнении плана требуется обычное подтверждение
шага по политике проекта. SSH-хост проверяется по `policy.network`.
Перед командой MAC-адреса гостя сверяются с настройками выбранной VM, чтобы
результат SSH и снимок окна относились к одной машине.
Для `127.0.0.1` действует разрешение localhost; другой IP добавьте явно в
`policy.network.authorized_targets`. Доступ к VM не разрешает атаки на
посторонние адреса: команды учебной работы должны обращаться только к
разрешённому стенду.

В существующем workspace задания:

```powershell
$ws = 'workspace/MyKaliLab'
$vm = 'kali-linux-2026.2-virtualbox-amd64' # точное имя из kali.list_vms
py -3.12 -m lab_agent.cli do $ws kali.list_vms
py -3.12 -m lab_agent.cli do $ws kali.status -p "vm=$vm"
py -3.12 -m lab_agent.cli do $ws kali.start -p "vm=$vm"
py -3.12 -m lab_agent.cli do $ws kali.screenshot -p "vm=$vm"
py -3.12 -m lab_agent.cli do $ws kali.run -p "vm=$vm" -p host=127.0.0.1 -p port=2222 -p user=kali -p "identity_file=$env:USERPROFILE\.ssh\doneasik_kali" -p 'command=id' -p 'expect=uid=' -p execution_id=check-id
```

Новый workspace сначала создайте обычным анализом материалов:
`py -3.12 -m lab_agent.cli analyze <папка-с-заданием>`; используйте возвращённый
путь workspace. `kali.start` не входит за вас в Kali и не настраивает SSH.
Графический сеанс должен принадлежать тому же пользователю, что и SSH.

Для большого сценария скопируйте UTF-8 `.sh` в `working/` workspace и вместо
`command` укажите `-p script=working/commands.sh`. Передаётся содержимое
копии, исходный файл сохраняется. Можно указать `cwd=/home/kali`,
`display=:0`, `xauthority=/home/kali/.Xauthority`, `timeout=120` (1–3600 секунд).
`expect` — буквальная подстрока вывода. Ошибка команды, таймаут, отсутствие
ожидаемого вывода или снимка не считаются успешным выполнением. Через `xprop`
проверяется, что терминал с уникальным названием стал активным окном Kali.
Скрытый другим гостевым окном терминал не подтверждает шаг.

В `results/` сохраняются команда, настоящий вывод и код завершения; в
`screenshots/` — снимок окна Windows; в `logs/commands.jsonl` — вызовы CLI.
Возвращённые доказательства регистрируются обычным механизмом SHA-256.
`kali.screenshot` снимает текущее окно и сам по себе не подтверждает выполнение
какой-либо команды. Перед сдачей проверьте, что нужный вывод виден на картинке.

В секции `kali` локального `config.yaml` можно сохранить поля `vm`, `host`,
`port`, `user`, `identity_file`, `display`, `xauthority`. Тогда одноимённые
параметры не нужно повторять в каждом вызове; явно переданные параметры имеют
приоритет. Файл содержит путь к приватному ключу, содержимое ключа в него
не записывается. Пример секции есть в `config.example.yaml`.

Результат команды сохраняется в `working/kali_*.json` до захвата окна.
Повторный запуск с тем же `execution_id` и теми же параметрами забирает
результат и исходный скриншот с проверкой его SHA-256 без повторного выполнения
команды. Если исходного снимка нет, перед повторным захватом проверяется,
что активен именно терминал сохранённой команды и заставка не закрывает его.
Для новой
команды задавайте новый `execution_id`. В плане идентификатор берётся из номера
шага. Если SSH оборвался и результат неизвестен, повтор блокируется: сначала
проверьте состояние гостя. При отсутствии явного `execution_id` каждый отдельный
вызов `do` считается новым запуском. Не закрывайте терминал до получения снимка;
после сбора доказательств его можно закрыть вручную. Рабочие файлы команды
остаются в гостевой `/tmp/doneasik-*` для проверки.

## Что делать при ошибке

- `Permission denied` / `Host key verification failed`: завершите ручную
  настройку SSH и убедитесь, что вход по ключу работает без запроса пароля.
- `Connection refused`: проверьте `sshd`, проброс порта и запущенную VM.
- `Can't open display`: проверьте X11-сеанс, пользователя, DISPLAY и XAUTHORITY.
- Пустой экран или нет окна: откройте окно самой VM, уберите сворачивание,
  разблокируйте графический сеанс. Запуск headless не даёт окна для PrintWindow.

Команды запуска VM сверены с [руководством VirtualBox](https://docs.oracle.com/en/virtualization/virtualbox/7.1/user/vboxmanage.html).
