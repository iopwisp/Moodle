# Выполнение assignment по просьбе «сделай»

Этот процесс обязателен для агента в этом репозитории. Пользователь присылает материалы
и просит сделать работу; агент ведёт её до проверяемого результата. Команды программы
помогают выполнить операции, но не заменяют понимание задания и проверку готового отчёта.

## 1. Разобрать материалы и критерии сдачи

- Найти приложенные файлы, инструкцию, шаблон и данные. Оригиналы не изменять.
- Прочитать инструкцию полностью, включая таблицы, изображения, приложения и рубрику оценки.
  Для PDF/DOCX использовать соответствующий доступный skill. Текстового извлечения недостаточно,
  если существенные требования находятся на рисунке или в таблице.
- Зафиксировать в workspace перечень требований: практические действия, вопросы, вычисления,
  нужные приложения/VM, скриншоты, формат, язык, имя сдаваемого файла и ограничения преподавателя.
- Приоритет имеют текущие указания пользователя и задание. Например, если нужен один PDF,
  сдаваемым файлом будет один PDF со скриншотами внутри; технический audit хранить отдельно.
  ФИО и группу брать из config; неизвестный Student ID не выдумывать.
- Задать только действительно блокирующий вопрос: недостающий обязательный файл, учётная запись,
  неоднозначность, которая меняет результат, либо неизвестный разрешённый стенд. Пока ответ
  не получен, продолжать независимые части. Не спрашивать повторно уже разрешённые действия.

## 2. Подготовить или продолжить workspace

```powershell
py -3.12 -m lab_agent.cli assignment <instruction.pdf> <data.zip>
py -3.12 -m lab_agent.cli context <workspace>
```

Если эта работа уже начата, сначала прочитать её `context`; продолжать тот же workspace.
Новый запуск создаёт копии материалов и детерминированный план без AI-вызова планировщика.
`metadata/assignment_brief.json` содержит извлечённые требования и незавершённые проверки
покрытия/отчёта. Сверить его с оригиналом и дополнить своим полным checklist в
`metadata/requirements_checklist.md`: требование → шаг/ответ → evidence/страница отчёта → статус.

Проверить capabilities и необходимые приложения только для выбранного задания. Использовать
готовый сценарий лишь когда он соответствует нужной последовательности; хеширование само
по себе не выполняет лабораторную. `--scenario scenarios/verify_image.yaml` — явный выбор
сценария вместо планировщика; его шаги и имена файлов надо проверить до выполнения.

## 3. Выполнить и проверить

До практических действий сверить и дополнить [план скриншотов](screenshot_checklist.md).
Сохранять ключевые состояния сразу в процессе, а не только в конце лабораторной.

Для сетевых лабораторных до выполнения создать [паспорт стенда](lab_passport.md) из реального
источника и проверить `context.lab_scope`. Область паспорта не расширяет policy; указать
разрешённые цели отдельно в config или через `--allowed-target` на нужных командах.
Не считать цитату доказательством владения и не добавлять посторонние адреса из списка литературы.

```powershell
py -3.12 -m lab_agent.cli assignment --workspace <workspace> --execute
py -3.12 -m lab_agent.cli do <workspace> <capability> -p key=value --step N
```

Перед `--execute` сверить план с заданием: параметры, зависимости, требования к evidence,
скриншотам и разрешённым целям. Команда исполняет существующие шаги через штатный runner,
policy и проверки, регистрирует evidence, сохраняет checkpoint и генерирует доступные отчёты.
По умолчанию AI-советы восстановления тоже отключены; другой провайдер выбирается явно.
Инструмент, который сам использует AI, может делать собственные вызовы.

Если шаг заблокирован, проверить причину и исправить доступную проблему. Не повторять
без изменений одну неудачную операцию. Если интеграции недостаточно, использовать доступный
консольный/GUI-инструмент и зарегистрировать настоящие результаты. Для GUI соблюдать
предупреждение о мыши/клавиатуре, skill и требование снимка реального окна программы.
Нельзя подменять окно программы изображением терминального вывода или нарисованным скриншотом.

Практические факты брать из наблюдаемого вывода. Теоретические ответы составлять по заданию
и требуемым источникам; не выдавать теорию за эксперимент. Ручные результаты добавлять через
`complete-step --verification ... --attach ...` только после наблюдаемого подтверждения.
Нельзя помечать неудовлетворённый шаг завершённым для обхода блокера.

При паузе/новом сообщении сохранять checkpoint. Логин, разблокировка экрана, недоступная VM
или файл требуют конкретного действия пользователя; кратко сообщить его и сохранить результат.

## 4. Собрать сдаваемый отчёт

- Проверить каждый пункт полного checklist, включая все вопросы и запрошенные скриншоты.
- Сверить каждый пункт `metadata/screenshot_checklist.json` с реальным кадром и рисунком
  в отчёте. Нехватку или нечитаемость обязательных кадров исправить до сдачи.
- Подготовить связный студенческий текст на языке задания по требуемому шаблону. Не отдавать
  технический журнал вместо лабораторной. Промежуточный автогенерированный отчёт не считается сдачей.
- Для обычного Markdown-процесса: `report.md` с YAML-шапкой → `build-report --strict` →
  `lint-report`. Если дан шаблон, заполнять его, сохраняя визуальную структуру.
- Проверить визуально все страницы финального файла доступным PDF/DOCX skill: подписи,
  скриншоты, переносы, таблицы, отсутствие пустых или обрезанных страниц. Проверить имя файла.
- Student report и audit хранить отдельно. Ссылаться только на реально существующие файлы.

## 5. Приёмка и ответ пользователю

```powershell
py -3.12 -m lab_agent.cli review <workspace>
py -3.12 -m lab_agent.cli context <workspace> --verify
```

`review.ready` означает техническую готовность выполнения и зарегистрированных evidence,
а не полноту assignment. Он проверяет статусы, подтверждения, обязательные evidence и
скриншоты, SHA-256 evidence, неизменность исходников и копий. Отдельно агент проверяет
полное покрытие оригинального задания, ответы, формат и визуальное качество отчёта.
После этих отдельных проверок обновить `coverage_review` и `report_review` в
`metadata/assignment_brief.json`: указать проверенный checklist, реальные имена итоговых файлов
и обнаруженные ограничения. Записи `pending` не заменять на успешные без выполненной проверки.

Считать задание выполненным только после всех этих проверок. Финальный ответ короткий:
что готово, ссылки на сдаваемые файлы, проведённые проверки. При блокере указать, что
осталось, почему и какое действие необходимо; частичный результат не называть готовой сдачей.
Коммит/пуш и отправку преподавателю выполнять только по отдельной просьбе пользователя.
